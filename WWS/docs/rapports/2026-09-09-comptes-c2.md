# Comptes C2 — serveur, 9 septembre 2026

## Résultat local

Inscription, connexion, déconnexion, lecture du compte et récupération administrateur sont
implémentées. Aucun parcours client ni rattachement aux parties n'est activé. Les joueurs,
leurs jetons et les changements du pillage S6c-1 sont conservés.

`auth.register` et `auth.login` sont des actions Node qui réutilisent les règles et le
hachage C1. Elles rendent seulement `{token}`. Le pseudo est unique après normalisation,
avec contrôle dans la transaction qui crée compte et session. Les jetons sont issus de
32 octets aléatoires, en base64url. Une collision est refusée sans écraser de session ni
laisser de compte orphelin. Un pseudo inconnu et un mauvais mot de passe rendent tous deux
`BAD_CREDENTIALS` ; le premier effectue aussi un PBKDF2 pour une saisie valide.

`accounts.me` rend seulement `{nickname}`, ou `null` pour une session absente/orpheline.
La query ne change pas la présence. `accounts.logout` est idempotente et ne supprime que
la session présentée. Plusieurs sessions coexistent sans expiration.

`auth.resetPassword` est une action interne réservée à l'administration. Sa transaction
remplace le digest et révoque toutes les sessions du compte. Une connexion commencée avant
le reset ne peut pas créer ensuite une session avec l'ancien secret : la transaction
compare le digest courant au snapshot vérifié. Si la connexion termine avant le reset,
celui-ci supprime sa session. La récupération ne crée ni compte ni session.

## Runtime et génération des types

Le module C1 réel a été exécuté directement sous Node v24.14.1 : hachage et deux
vérifications en 174 ms, mot de passe correct accepté et incorrect refusé. Les tests C2
utilisent l'environnement Node de Vitest ; le banc `convex-test` simule les transactions,
il ne prouve ni l'OCC ni le runtime du backend installé sur le VPS. Les actions Node isolent
le coût PBKDF2 des mutations rejouables. Les sources officielles justifiant ce choix sont
liées dans le [brief C2](../prompts/code/done/comptes-c2-serveur.md).

**Aucun codegen automatique réussi.** `npx convex codegen --typecheck disable` a tenté six
fois de joindre `http://127.0.0.1:3210`, puis échoué avec `Unable to pull deployment config`.
La solution locale a été une mise à jour mécanique minimale de `convex/_generated/api.d.ts` :
deux imports de types, `accounts` et `auth`, et leurs deux entrées dans `ApiFromModules`.
Le fichier JavaScript utilise déjà le proxy générique et n'a pas changé. TypeScript valide
ces références. Cette solution ciblée ne remplace pas le codegen des composants Convex.

La classification exhaustive est dans **`convex/dev.ts`** : `GAME_TABLES` et
`IDENTITY_TABLES = ['accounts', 'sessions']`. Le test de **`convex/season-partition.test.ts`**
vérifie leur disjonction et l'égalité de leur union avec les tables du schéma. Toute future
table doit donc être classée explicitement. La fixture de destruction exhaustive du
hors-saison peuple les tables de jeu ; le test C2 prouve séparément la survie des identités.

## Limites et suite

Pas de limitation de débit ni d'expiration automatique, conformément au brief accepté ;
risque consigné. `lastSeenAt` est initialisé uniquement, sans présence client avant C3.
Aucun compte ne possède encore de place ; `me` ne prétend donc pas en servir une liste vide.
Le rattachement, les portes de jeu et l'interface attendent C3. Le sort des places historiques
reste à décider avant activation, sans attribution par pseudo ni effacement implicite.

Aucun worktree, commit, push, déploiement ou effacement de données en service. L'auteur et
le relecteur C2 ont arrêté leurs écritures. Après fermeture documentaire, les écritures sont
rendues explicitement à « Suite du pillage S6a » ; C3 ne démarre pas dans ce créneau.
