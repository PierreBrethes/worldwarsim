# Comptes C1 — 9 septembre 2026

## Résultat

Les règles communes d'identifiants et le hachage sont livrés dans quatre nouveaux fichiers :

- `src/domain/account.ts` et `src/domain/account.test.ts` ;
- `convex/passwords.ts` et `convex/passwords.test.ts`.

Le pseudo conserve ses accents à l'affichage, après retrait des espaces de bord et
normalisation NFC. Sa longueur est bornée à 3–16 points de code. Les caractères de contrôle
et de format sont refusés avant le retrait des espaces ; une clé vide après suppression
des marques combinantes est refusée. La clé d'unicité est en minuscules, sans marques
combinantes après NFD.

Le mot de passe reste inchangé. Ses bornes sont 8–72 octets UTF-8. Le serveur fournit
PBKDF2-SHA-256 à 600 000 itérations, avec un sel aléatoire de 16 octets et un résultat de
32 octets, sérialisés en base64url canonique sans remplissage. La vérification utilise les
itérations stockées, refuse un digest malformé et propage une panne de Web Crypto.
La comparaison parcourt les 32 octets sans arrêt précoce lié à une différence ; ce n'est
pas une promesse de temps physiquement constant sur tous les moteurs JavaScript.

## Réserve de runtime

Le code Rust officiel amont confirme PBKDF2-HMAC-SHA256 et transmet un facteur non nul sur
32 bits à la primitive native. Cela établit le support amont des paramètres choisis, pas
la version ni les performances du backend installé.
[Source Convex, relue le 9 septembre](https://github.com/get-convex/convex-backend/blob/main/crates/isolate/src/ops/subtle_crypto/pbkdf2.rs).

Le compose du dépôt utilise l'image `:latest`. Ni la version réellement installée sur le
VPS, ni son coût de calcul n'ont été vérifiés. Les tests `edge-runtime` restent une preuve
locale. La documentation publique indique un budget d'exécution du code utilisateur pour
les mutations ; son applicabilité au backend auto-hébergé et le coût réel du hachage doivent
être vérifiés avant les portes publiques de C2.
[Limites Convex](https://docs.convex.dev/production/state/limits).
